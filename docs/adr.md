## ADR-1 任务终态由引擎设置，框架不兜底写终态

**状态**：已采纳

**背景**：任务失败有两条可能通路——引擎明确判定失败，或引擎返回 error 由框架兜底置 failed/canceled。若框架在 error 时立即落盘终态，瞬态错误（网络抖动、暂时不可用）会永久终结任务，断掉恢复路径。

**决策**：唯一落盘失败路径是**优雅失败**——引擎在 `Execute` 内置 `PhaseFailed` 并返回 nil，框架 Save 后停止。`Execute` 返回非 nil error 表示可重试/可恢复：进程内重试耗尽后 Run 返回 error **不落盘**，任务停留于最后已提交阶段，下次 Run 从该阶段恢复。框架不写任何终态；ctx 取消同样不落盘。不设 canceled 枚举（无写入方的终态值不得进入模型；需要取消语义的引擎可在自身 PhaseSet 中声明取消阶段并自行置位）。

**理由**：只有引擎知道错误是否永久；「未完成 vs 失败告终」的区分由「持久化 failed 只能来自引擎显式判定」天然保证。

**后果**：重试耗尽且不再重跑的任务在存储上呈现为非终态（等价于崩溃中断），运维需通过引擎 Message/日志或重跑判定；引擎必须在可判定失败时显式置 failed，这是引擎契约义务。

## ADR-2 原子写全库唯一实现

**状态**：已采纳

**背景**：任务状态后端与 outbox 消息后端都需要 tmp→Sync→Rename 原子写。两处独立实现会随时间漂移（错误包装策略、失败清理路径各自演化），崩溃安全这一关键性质无法统一保证。

**决策**：库内提供唯一原子写原语 `internal/atomicfile`（tmp→Sync→Rename，可选父目录 fsync）；`filestore` 与 `outbox/filestore` 一律复用。任何持久化组件不得私写临时文件逻辑。

**理由**：崩溃安全关键逻辑复制多份必然漂移；单一实现使「半写文件不存在」这一不变量只在一处维护与测试。

**后果**：后端文件布局差异（每任务一文件 vs 每消息一文件）由各后端自持，原子写内核共享；新后端（DB/对象存储）实现 `StateRepository`/`Store` 接口即可接入。

## ADR-3 中间产物清理：调用方显式 Cleanup 且错误可见

**状态**：已采纳

**背景**：分块文件是崩溃恢复的重放输入，删除时机错误（终态落盘前）会使 completed 无法重放；同时清理自身的失败（目录不可读、删除失败）若被静默吞掉，磁盘泄漏不可见。

**决策**：分块与残留临时文件的删除必须推迟到 completed checkpoint Save 成功之后，由**调用方显式调用 `Cleanup()`**；框架不自动清理（框架不认识引擎私有产物）。`Cleanup() error` 返回错误，目录读取与删除失败不得静默丢弃。

**理由**：清理是破坏性动作，与状态转换不得同事务步；显式调用让时序契约可见，错误可见让泄漏可发现。

**后果**：调用方遗忘 Cleanup 只造成磁盘残留（孤儿临时文件可在下次构造时清理），不影响正确性；协议顺序（终态 Save → Cleanup）写入组件契约文档。

## ADR-4 Saga 恢复校验步骤定义指纹

**状态**：已采纳

**背景**：Saga 执行状态按步骤索引记录（StepStatuses/CurrentStep）。若恢复时传入的定义与持久化状态错位（步骤增删/重排），轻则补偿错步骤，重则索引越界。

**决策**：`Run` 时计算步骤名序列的稳定哈希（SHA-256，名称以 `\x00` 连接）写入 `SagaState.StepFingerprint`；`Resume` 校验传入定义的指纹与持久化值一致，**不一致拒绝恢复**并返回错误。

**理由**：校验成本一次哈希，错位风险是补偿错误执行（不可逆操作的错误补偿）。

**后果**：修改步骤序列后旧 saga 不可 Resume，需新建 saga 实例（与「防错引擎恢复旧状态」的 TaskType 校验同一原则）；步骤实现变更但名称不变不在校验范围内（行为兼容由 Action 幂等契约保证）。

## ADR-5 引擎重试以快照为起点

**状态**：已采纳

**背景**：`Execute` 收到 `*BaseTaskState` 指针，可在失败前已部分修改 Payload/Message/Phase。若失败调用把污染的状态传入重试，重放语义不可推理；仅靠引擎自律（先做完可失败操作、最后才改状态）无法在框架层保证。

**决策**：框架在**每次 Execute 前深快照**整个 BaseTaskState（含 Payload 字节——json.RawMessage 可拷贝），Execute 返回 error 时**回滚到快照**再重试；重试耗尽后状态停留在最后已提交 checkpoint，返回 error 不落盘。

**理由**：把「重试起点 = 本步进入前状态」从引擎自律升为框架保证；快照成本是每步一次结构体+字节拷贝，相对物理副作用可忽略。

**后果**：引擎内不需要防御性回滚；引擎仍须保证**物理副作用**幂等/可对齐（快照只覆盖框架状态，不覆盖外部系统）。

## ADR-6 Store 契约（processing 重取、单分发器）与便捷方法保留

**状态**：已采纳

**背景**：消息处理中崩溃后必须重投（at-least-once），语义落点是 FetchPending 是否返回 processing 消息；同时并发多分发器会同时取走同一消息。契约若不显式声明这两点，实现方各自猜测。此外 Store 有 UpdateStatus 与 MarkProcessed/MarkFailed 两个层次，存在瘦身诱惑。

**决策**：
1. Store 契约显式声明：**FetchPending 返回 pending 与 processing 消息（无条件重取，无超时/租约机制）**，处理中崩溃后下次拉取重投。
2. **单分发器前提**写入契约：同一 Store 同时只允许一个 Dispatcher；多分发器需租约机制，不在范围内。
3. 保留 `MarkProcessed`/`MarkFailed` 便捷方法（调用方高频、语义清晰），实现方以 `UpdateStatus` 组合实现；幂等语义统一为「仅目标不存在视为成功，IO 故障返回错误」。
4. 契约不得描述无字段支撑的行为（无租约时间戳就不得声称「超时重取」）。

**理由**：重取语义是 at-least-once 的实现核心，必须唯一且显式；便捷方法降低调用方样板，重叠成本由实现方内部组合吸收。

**后果**：多 Dispatcher/多进程分发场景被明确排除（非目标）；未来需要多分发器时引入 `ProcessingSince` 时间戳 + 租约超时，属破坏性契约扩展。

## ADR-7 一切处理回调携带 ctx

**状态**：已采纳

**背景**：调度层回调存在两套签名——saga 的 Action/Compensation 携带 ctx，outbox 的 Handler 不携带。执行不可逆外部操作（发邮件、扣款）的回调反而无法感知取消，长阻塞 Handler 无法被停止。

**决策**：统一为 `func(ctx context.Context, msg Message) error`（值语义——Handler 只读，状态迁移经 Store 进行）；Dispatcher 调用时传入分发 ctx。消息在 Append 入参、FetchPending 返回、Handler 入参与 Accumulator.Messages 返回处全链路按值传递/拷贝，存储内部状态不经指针外泄。一切处理回调（Handler、Action、Compensation）接收 context 并响应取消，写入全库约束。

**理由**：回调执行的是最可能阻塞的外部 IO；签名不一致是同一层概念多套叫法的直接来源。

**后果**：Handler 实现方需处理 ctx 取消（幂等语义下取消后重投安全）；这是对早期签名约定的破坏性变更，新项目首版即定，无兼容负担。

## ADR-8 通用文件能力下沉库内，垂直引擎独立扩展包

**状态**：已采纳

**背景**：分块写文件、截断重放、偏移行读取、原子合并是跨业务可复用机制；而分页导出、幂等入库是垂直业务编排。机制与业务若同处一层，要么机制被锁进示例无法复用，要么业务词汇渗入核心框架。

**决策**：
1. **下沉库内**（`stream` 包）：`ChunkedSink`（分块文件汇：截断重放 + Stater + Finalize 原子合并 + Cleanup）与 `OffsetSource`（偏移行源：含分隔符字节计数 + 源侧 Align）。原子写原语下沉 `internal/atomicfile`（见 ADR-2）。
2. **独立扩展包** `datapipeline`（依赖核心、核心不依赖、独立版本）：`export`（分页 Source 适配 + ChunkedSink 组合）与 `ingest`（OffsetSource + 幂等目标）垂直引擎；`Row/DataSource/DataTarget` 随扩展包，不进核心。

**理由**：分块导出经下沉后无需中间业务阶段——Finalizer 在源耗尽时收尾，`DefaultPhaseSet` 即可覆盖全程，消解了「为业务阶段扩枚举」的历史压力；业务编排独立演进不牵动核心版本。

**后果**：核心库对「文件管道」提供开箱即用组件（batteries-included），但抽象保持泛型；扩展包是参考级实现，调用方可替换任一侧适配器。

## ADR-9 Saga 终态三分与补偿可重试/可超时

**状态**：已采纳

**背景**：补偿面对与正向同样的易失败外部系统：单个补偿可能瞬态失败（应重试）或永久挂死（应超时）；单个补偿失败不应阻断其余补偿。终态若不区分「补偿全部成功（已回滚，无需人工）」与「补偿失败（需人工介入）」，运维无法从持久化状态分流。

**决策**：
1. `SagaStatus` 终态三分：`completed`（全部正向成功）/ `compensated`（正向失败、补偿全部成功）/ `failed`（任一补偿失败，需人工介入）。
2. 补偿沿用步骤的重试链（step → saga 默认 → 1）与超时施加方式（`context.WithTimeout`）。
3. 单个补偿失败记入 StepErrors 后继续其余补偿，不阻断。
4. 原始失败原因与补偿失败原因均持久保留于 StepErrors。
5. 取消路径以 `context.WithoutCancel` 保存状态；一切 Save 错误检查并上抛，不吞。

**理由**：三分终态使「已回滚干净」与「需要人来」在存储层可判；补偿不强化则 saga 在补偿期失去进度保证（挂死或一步失败全盘放弃）。

**后果**：`failed` 语义收窄为「补偿失败需人工介入」（正向失败已回滚的是 `compensated`）；消费方按三分终态分流告警；补偿失败可经人工重置步骤状态后 Resume 重试。

## ADR-10 便捷糖收敛组合边界；绑定指纹 fail closed

**状态**：已采纳

**背景**：examples 暴露「状态目录 + 组件构造 + Run」链条无处收口，每个场景 3~7 句样板。同时，taskID 与源/产物/引擎存在三重关联：id×引擎已有 TaskType 校验，id×产物/源路径却无任何机制——同 taskID 换路径重跑会静默错乱（分块残留旧路径、游标对不上新路径）。

**决策**：
1. 糖收敛在根包 `waypoint` 的组合边界：`Task` 世系句柄绑定（状态目录 × 引擎 × taskID），`Run`/`RunWithOutbox` 只传 ctx（+可选重试）。糖只承载**易用性**——缩短正确用法，不拦截错误用法（同进程构造错配 Task 无法判定意图）；安全主张由机制承载：TaskType 校验（防跨引擎）+ **绑定指纹**（防同引擎换路径）。
2. **绑定指纹**：export 指纹产物路径、ingest 指纹源文件路径（SHA-256），写入各自自持命名空间；首个 checkpoint 必须携带（pending→running 步即写入，堵住「crash 于首个 checkpoint 后无指纹可校验」窗口）；恢复时**缺失即拒（fail closed，留白等于绕过校验）**、不一致即拒；挂点在 Execute 首步（Aligner 契约只传 LSN，且源侧 Align 无副作用，前移无安全收益）。id×源内容无法机制化（接口值无稳定身份），为契约。
3. outbox 排空便利命名为 `DispatchUntilIdle`——诚实表达「无进展即停、不保证排空」；不叫 Drain（过度承诺）。
4. 糖的准入门槛是繁琐度（≥3 句样板）；saga 调用已足够简短，不配糖。
5. 非目标：Task 不提供 Delete；根包不 re-export `state` 常量；不做 Kit/Builder 门面；不自动 Cleanup、不自动分发（ADR-3 与 §6.3 责任归属不变）。

**理由**：把安全收益错误归因给糖（「Task 让错误用法不可能」）会诱导虚假信任——断点续传主场景是跨进程重建，届时三元组一致仍是契约，真正拦截错配的是指纹。指纹的三个实现细节（首 checkpoint 覆盖、缺失即拒、挂点）任何一个留白都会让机制失效或留下绕过口。

**后果**：跨进程恢复必须以相同三元组重建 Task（产物/源路径错配被指纹拒绝；源内容同路径被换属调用方违约，部分场景由源侧大小校验兜底）；指纹校验失败是可重试 error，`WithRetry` 会空转耗尽（不落盘语义正确）；终态任务不校验指纹（Run 直接返回、无副作用）；一产物路径一世系为文档契约（多世系共享输出路径互踩分块，指纹拦不住各自的自洽绑定）。
